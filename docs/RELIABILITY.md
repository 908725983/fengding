# 启动与验收

## 环境基线

- Windows PowerShell 7 或兼容版本
- Node.js 20.19+ 或 22.12+（本仓验证使用 Node 24）
- npm

## 标准命令

```powershell
./scripts/init.ps1       # 缺依赖时安装，然后执行全部验证；不修改 Mock 现场
./scripts/start.ps1      # 启动本地原型
./scripts/verify.ps1     # Harness + 类型 + 测试 + 构建
./scripts/reset-mock.ps1 # 恢复确定性 Mock 状态
```

等价 npm 命令：`npm start`（或 `npm run dev`）、`npm run verify`、`npm run mock:reset`。

## 干净重启

1. 停止开发服务器。
2. 仅在需要恢复确定基线时运行 `./scripts/reset-mock.ps1`；恢复中断任务时保留现场。
3. 运行 `./scripts/init.ps1` 验证依赖和代码。
4. 运行 `./scripts/start.ps1`。
5. 打开终端显示的本地地址，确认应用壳、侧栏和 Dashboard 可见。

干净重启用于工程基线、L3 高风险批次、共享 Runtime 改动和发布前收尾；普通 L1/L2 小切片不在每个功能完成时重复执行。一个业务批次收尾执行一次即可。

## 基线黄金旅程

1. 页面载入后显示“蜂订业务原型”与八个有详细规格的导航领域。
2. Dashboard 显示当前阶段、Harness 检查项和模块规划状态。
3. 点击任一未开发模块，显示其规格入口和“规划中”，不展示虚构业务数据。
4. 1280px 宽度下侧栏和主内容可用；应用壳窄屏导航单独验证一次，不把普通 PC 业务页的 390px 布局设为完成条件。
5. 运行 `npm run verify`，所有检查通过。

## 业务验证分级

验证按风险选择，不再要求每个页面重复一套九场景：

| 等级 | 典型范围 | 自动证据 | 人工证据 |
|---|---|---|---|
| `L1` | 只读列表、报表、标准主数据 CRUD | 契约、查询/保存、empty、校验、适用权限 | 一个代表性正常任务；布局明显不同才追加页面检查 |
| `L2` | 单领域状态机、导入导出、可恢复编辑/删除 | L1 + error/retry、合法/非法转换、关键边界、失败现场不变 | 一个完整状态旅程和错误恢复 |
| `L3` | 金额、库存、结转、跨域写入、不可逆动作 | L2 + 幂等、并发、原子回滚、数量/金额守恒 | 从 reset 开始的完整黄金旅程、代表性 1280px 页面和批次收尾干净重启 |

公共能力只验证一次：

- `loading/slow/retry` 由共享异步状态与基础组件测试覆盖，业务页只在有特殊超时行为时追加。
- `partial-failure` 仅用于同时聚合多个可独立失败 provider 的页面。
- `unavailable` 仅用于明确未接入的跨域或第三方能力。
- `concurrent` 仅用于可并发修改的状态单据和 L3 写操作；普通只读页、静态资料页不制造并发场景。
- `permission-denied` 必须覆盖真实权限边界，但可由 Service/路由自动测试承担；不要求每个页面手工切换五种角色。

开发阶段运行最小相关测试；规格变更后运行 `npm run verify:harness`；一个业务批次收尾才运行一次 `npm run verify`、需要的 Mock reset、代表性浏览器旅程和干净重启。证据写入 active plan，记录命令、结果、关键测试、旅程、失败修复和重跑结果；截图仅用于关键视觉或难以自动断言的事实。

## 完成声明的三个层级

| 层级 | 可以证明什么 | 不可以据此宣称什么 |
|---|---|---|
| 模块通过 | 单个切片的字段、规则、页面、Repository 和 Service 可用 | 关联模块已共享数据 |
| 集成通过 | 两个或多个领域在同一共享 Mock Runtime 中完成一次交接 | 整个阶段的全部用户任务已闭环 |
| 业务闭环通过 | 从本次新建源头单据到最终单据和余额结果全部可重复 | 真实 API、数据库和第三方生产能力已验证 |

质量评分和完成计划必须使用这三个名称，不得把多个模块分别通过合并描述为业务闭环通过。

## 跨模块黄金旅程

跨模块计划除前述七层外，还必须满足：

1. 运行 `npm run mock:reset` 后启动一套应用级共享 Mock Runtime；记录场景、受控时钟和 Runtime/测试实例标识。
2. 允许 fixture 提供主数据，但源头和下游业务单据必须在本次旅程中创建。销售收款主路径不得预置订单、出库、应收、收款或核销；采购付款主路径不得预置采购单、入库、应付、付款或核销。
3. 全程记录同一链路的业务编号和内部关联 ID；每个下游单据必须能追溯到上一步，不能在下一模块换用另一张预置单据。
4. 路由切换后读取同一业务状态。业务 Store 重新克隆 fixture、模块分别创建 Mock session 或跳转后丢失上游新数据，均判定集成失败。
5. 核对数量、金额、账户、应收应付和状态守恒；同时检查失败注入后所有相关 Repository 均未留下半完成状态。
6. 至少保留一项跨领域 Service 集成测试和一条浏览器端到端旅程；组件测试、模块截图或相同 baseline 哈希不能替代它们。

销售与收款证据至少记录：`订单号 → 销售出库单号 → 应收单号 → 收款单号 → 核销单号`。采购与付款证据至少记录：`采购单号 → 入库单号 → 应付单号 → 付款单号 → 核销单号`。

## 故障处理

- 安装时若全局 npm 缓存无写权限，脚本会将缓存切换到仓库 `.npm-cache/`。
- `init.ps1` 不会自动重置 Mock，避免任务恢复时丢失现场；测试必须自行隔离数据。
- Harness 检查失败时先修链接、状态或规格，不跳过 `verify:harness`。
- Mock 状态异常时重置，不手工修改 baseline 来让单次测试通过。
- 构建失败时不得把功能标为 `passing`。

## 可观测与诊断

- 异步动作记录场景、领域动作、结果和可定位的错误代码，不记录敏感字段。
- 页面显示用户能理解的失败原因与重试入口；开发日志可以补充调用耗时和关联 ID。
- Mock handler 必须能稳定切换 normal、empty、error、slow 与 permission-denied，禁止靠随机失败复现问题。
- 诊断脚本与说明留在仓库内；只有聊天里提到过的排查知识不算可恢复。

## 禁止的“假通过”

- 不得用固定展示数据绕过 Repository/Service 后宣称业务完成。
- 不得删除失败测试、放宽断言、跳过 error/permission-denied 场景或手改 baseline 来取得通过。
- 不得把 Mock 外部调用的成功提示描述成真实支付、消息、地图、企微或文件已成功。
- 不得把 `npm run build` 通过等同于字段、规则、权限或业务黄金旅程通过。
- 不得用相同 fixture baseline 的不同内存副本冒充共享数据，也不得用预置上下游单据拼接成端到端闭环。
- 不得在缺少同一新建业务单据的关联编号、守恒表和跨路由可见证据时，把阶段状态标为 `passing`。

## 原型不证明的内容

本验收不代表真实 API、数据库并发、在线支付、消息到达、地图定位、生产权限安全和审计合规已验证。
