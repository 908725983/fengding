# 原型实现顺序

- 状态：Accepted
- 最近更新：2026-08-24

## 职责

本文件只决定“先做什么、为什么、阶段如何退出”。`../product-specs/index.md` 是全部功能、来源、依赖和规格准备度的唯一目录；`../QUALITY_SCORE.md` 是当前质量与完成证据入口；`../exec-plans/active/` 保存当前切片现场。

## 切片与批次开工门

业务切片进入代码实现前必须同时满足：

1. 功能 ID 存在于产品规格索引，且所有依赖已有 passing 证据。
2. 字段准备度为 `ready`，对应领域规格存在完整的“`<功能ID> 字段与交互契约`”。
3. 所有阻塞该切片的人工决策已变为 `decided`；未受影响的部分可以继续规格提取。
4. `docs/exec-plans/active/` 中存在唯一业务 active plan，写明一个或多个功能 ID、阶段、风险等级、精确来源和验证路径；`business-batch` 中每个功能分别满足本门禁。
5. `npm run verify:harness` 基线通过。

`source-only` 只允许进入 specification；`blocked` 不建立执行计划；`ready` 也必须满足依赖和 active plan 门禁后才能编码。

任何一项不满足，都不允许为了展示进度先写一个“看起来像完成”的页面。

## 阶段一：销售基础事实

严格顺序：

1. `CUS-001` 客户档案、分类与标签。
2. `PRD-001` 商品、SKU 与多单位。
3. `PRD-002` 价格体系与调价。
4. `PRD-003` 商品授权。
5. `INV-001` 库存查询、仓库、库位与批次。

顺序理由：订单必须先能回答“客户是谁、商品是什么、使用什么单位和价格、客户是否有权购买、出库时是否有可用库存”。客户编码/状态、单位换算、授权冲突和库存状态边界分别受产品目录中的决策门约束。原始需求没有库存预占规则，禁止在本阶段自行添加预占；仅实现已确认的出库扣减。

阶段出口：对指定客户和 SKU，可解释地返回授权、价格来源、单位和当前可用库存；所有结果来自领域 Service，而不是页面临时数组。

## 阶段二：销售与收款闭环（模块与核心集成已完成）

1. `ORD-001` 客户订单列表与详情。
2. `ORD-002` 新增与修改订单。
3. `ORD-003` 订单审核与状态流转。
4. `ORD-004` 销售出库、发货与差异。
5. `FIN-003` 资金账户、银行与结转基础。
6. `FIN-001` 客户应收、收款与核销。
7. `ORD-005` 客户退单与退款。
8. `ORD-006` 订单与销售统计。

进入 `ORD-002` 前解决价格组合、客户状态、单位换算、授权冲突和预收占用；进入 `ORD-003` 特价分支前解决特殊审批；连接 `ORD-004` 与 `FIN-001` 前解决应收形成时点；连接退货、入库和退款前解决相应跨域决策。未决时可完成互不依赖的页面和只读契约，但不得伪造跨域结果。

阶段出口：同一个应用级共享 Mock Runtime 可以从本次新建业务单据重复完成“选客户与商品 → 建单 → 审核 → 出库/发货 → 应收 → 收款核销”，并以同一订单的出库、应收、收款、核销编号和金额守恒为证据；失败不会留下半完成库存或资金状态。`FLOW-SALES-001` 已于 2026-08-24 通过共享 Runtime integration 验收。

## 阶段三：采购、库存与资金闭环

采购主线：

1. `PUR-004` 供应商与直送供应。
2. `PUR-001` 补货分析与快速采购。
3. `PUR-002` 采购订单与入库。
4. `FIN-002` 供应商应付、付款与核销。
5. `PUR-003` 采购退单。
6. `PUR-005` 采购统计（已完成并归档）。

库存与资金扩展（依赖满足后按以下顺序）：

7. `INV-002` 转仓与其他出入库。
8. `INV-003` 盘点、成本调整与库存结转。
9. `INV-004` 加工管理。
10. `INV-005` 分拣与配送。
11. `INV-006` 库存统计。
12. `FIN-004` 退款、转账与其他收支。
13. `FIN-005` 机构收款与资金统计。

进入补货结果前解决补货公式，进入采购状态机前统一订单/入库状态表达，进入带成本入库前解决加权成本口径，进入应付集成前解决应付形成时点；进入采购退单校验前确认是否强制关联原采购单。阶段出口是同一个共享 Mock Runtime 从本次新建需求/采购单重复完成“库存/订单需求 → 采购 → 入库 → 应付 → 付款核销”，所有库存和资金变化都能由本次创建的业务编号追溯。`FLOW-PURCHASE-001` 已于 2026-08-24 通过共享 Runtime integration 验收。

执行批次约束：

- `INV-003` 涉及盘点、成本和期间锁，保持独立 L3 计划。
- `INV-004` 加工和 `INV-005` 分拣配送都是大型状态机，分别实现并保留独立回退点；`INV-006` 在两者完成后统一消费库存事实。三个库存切片只在库存扩展批次末尾做一次全量验证、浏览器回归、Mock reset 与干净重启。
- `FIN-004 + FIN-005` 作为资金扩展批次，共用账户、退款和统计事实；退款必须复用 `ORD-005/FIN-001` 既有 owner，不能重复创建第二套退款状态机。
- 共享 Runtime 整改使用一个 integration 计划统一修复组合根，并在同一计划中分别验收 `FLOW-SALES-001`、`FLOW-PURCHASE-001`、`FLOW-RETURN-001`。三条流程仍独立记录状态，不能互相替代。

## 阶段四：组织与运营扩展

后续按业务批次推进：

1. 设置基础资料批次：`SET-001 + SET-003`。公司、部门、公告和区域共用组织资料；`SET-003` 的仓库入口必须复用 `INV-001` 的唯一仓库事实，不建立第二套仓库 Repository。
2. 权限与审计批次：`SET-002 + SET-004`。角色、员工、权限树与系统日志共享操作者和权限事实。
3. 商品辅助资料批次：`PRD-005`。分类、品牌、单位、标签、智能标签和展示分类使用一套标准主数据模式与一次批次验收；已完成的 `PRD-004` 不重复执行。
4. CRM 运营批次：`CUS-002 + CUS-004 + CUS-005`。商机、常购、地图、公海和外勤共享客户、业务员与区域事实。
5. 会员体系批次：`CUS-003 + CUS-007`。会员等级、权益与积分共同固定结算输入和积分账本。
6. 营销闭环批次：`CUS-006 + CUS-010`。优惠券、促销、内容获客与营销分析共享活动事实；依赖会员体系后再进入实现。
7. 外部渠道原型批次：`CUS-008 + CUS-009`。企微和商城只实现 PC 管理端配置、预览和明确 fake adapter，不建设真实第三方或完整移动应用。
8. `PRD-006` 关联商品推荐只有一句规则，已标为 blocked；补充配置入口、关系模型、触发、排序、数量和权限后才恢复。

只要产品规格索引中的依赖已通过，设置、商品运营和客户经营批次可以调整先后，但同一时间仍只推进一个业务计划。批次内部为每个功能 ID 保留独立检查点和完成结论。实现默认角色前必须解决“部分权限”的细权限映射；企微、地图、消息、AI、在线支付和真实文件继续使用 fake adapter。

阶段出口：模拟角色看到正确菜单和操作，配置由唯一领域事实驱动，运营功能不绕过商品、订单或资金规则。
