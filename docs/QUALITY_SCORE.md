# Harness 质量审计

- 最近审计：2026-08-10
- 审计对象：业务 coding 前的工程基线
- 结论：可开始 `CUS-001`，不代表业务系统或生产能力完成

## 审计结果

| 维度 | 状态 | 证据 | 剩余风险 |
|---|---|---|---|
| AI 入口与知识路由 | 通过 | `AGENTS.md` 保持短入口，链接到专业文档 | 新文档必须同步导航，避免孤儿知识 |
| 需求可移植性 | 通过 | 八份需求快照、SHA-256 manifest、上游变化检测 | 上游变化仍需人工评审，不能自动覆盖规格 |
| 产品范围覆盖 | 通过 | 46 项功能覆盖八领域主要子模块，商家/独立分析明确 blocked | 字段在功能开始前按需提取，不提前复制全部需求 |
| 规则可追踪性 | 通过 | ORD/PRD/PUR/INV/CUS/FIN/SET 全部规则 ID 同时进入规格与功能清单 | 新规则必须分配 ID 并更新机械检查 |
| 功能依赖 | 通过 | `depends_on` 可验证不存在、无循环、且开工前已 passing | 路线图顺序变更必须同步 JSON 依赖 |
| UI 一致性 | 通过（基线） | 前端规范、Token、字段模板、1280/720 浏览器检查 | 尚无业务页面，具体字段规格将在每项功能开始前验收 |
| Mock 可重复性 | 通过（基线） | 固定 fixture、五类场景、显式 reset | 应用尚未实现业务 repository，不能证明跨领域事务 |
| 中断恢复 | 通过 | progress、active plan 模板、恢复点、completed 证据 | 开发者必须在中断前真实更新恢复点 |
| 机械验证 | 通过 | Harness、类型、3 个测试、生产构建 | 业务代码增加后需要扩充规则测试和架构检查 |
| 安全边界 | 通过（原型） | `SECURITY.md`、fake adapter、无真实数据规则 | 不代表生产安全；真实集成必须重新设计 |
| 版本控制 | 通过 | 独立 Git 仓库、`.gitignore`、`.gitattributes` 和 Harness 基线提交 | 后续功能仍需保持小范围、可审查提交 |

## 允许开工的条件

当前允许开始 `CUS-001`，因为其依赖 `SHELL-001` 已 passing。开工动作仍需依次完成：提取客户页面 `ui_spec`、创建 active plan、检查开放问题、把功能设为唯一 `in_progress`，然后运行 Harness 验证。

## 不允许宣称的内容

- 不能说订单、库存、资金等业务已经实现。
- 不能说 Mock 权限等于真实安全。
- 不能说所有页面字段已经提取；当前采用逐功能门禁。
- 不能说真实接口、支付、消息、地图、企微、文件和 AI 已验证。
- 不能因为构建通过就把业务功能标记 passing。

## 下次审计触发条件

完成每个路线图阶段、改变架构边界、引入真实 API/新依赖、修改状态或金额库存规则、发现需求快照变化时，更新本文件并重新运行完整验证。
