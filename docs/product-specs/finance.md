# 资金领域规格

## 需求来源与事实边界

- 直接业务来源：[07-资金模块.md](../references/requirements/07-资金模块.md)；业务闭环、全局交互与角色资料来自 [01-整体架构与首页.md](../references/requirements/01-整体架构与首页.md) §2、§4～§5。
- 功能切片、章节、依赖、规则归属和字段准备度以 [产品规格索引](index.md) 为唯一目录。
- `FIN-01～FIN-11` 直接整理自原文 §10。“不变量”中的整数分、原子流水和幂等属于 Harness 工程约束。
- 原文没有明确应收/应付形成时点，退款与退货入库的跨域账务关系也不完整，应付账龄区间和逾期边界没有完整定义；相关集成分别按 `DEC-FIN-001～004` 处理。

## 目标与范围

跟踪客户应收、供应商应付、收付款、核销和资金账户，使业务单据与资金变化能够相互追溯。

## 主要页面

- 应收/应付列表、按单据/商品明细、账龄分析。
- 核销单列表、新增与明细。
- 收款、付款、退款确认、拉新提现。
- 资金账户、收支明细/汇总、结转、银行和在线支付设置。
- 内部转账、其他收支、机构收款和资金统计。

## 业务规则

| ID | 必须行为 |
|---|---|
| FIN-01 | 收付款与应收应付单据进行匹配核销。 |
| FIN-02 | 按单据日期自动计算账龄区间。 |
| FIN-03 | 每笔确认收付款实时更新资金账户余额。 |
| FIN-04 | 已核销收付款不可删除或修改金额。 |
| FIN-05 | 退款优先原路；特殊情况可选择现金或余额。 |
| FIN-06 | 已资金结转月份禁止资金出入。 |
| FIN-07 | 非业务收付款必须财务审核。 |
| FIN-08 | 转账只允许内部资金账户之间调拨。 |
| FIN-09 | 支持第三方支付通道开通配置。 |
| FIN-10 | 拉新奖励提现审核后打款。 |
| FIN-11 | 多机构模式按机构汇总收款。 |

## 不变量

- 金额为整数分；收付款、已核销、未核销三者关系必须精确且不可为负。
- 一次核销可匹配多张单据，但总核销额不得超过可用收付款额或单据未核销额。
- 账户余额变化和资金流水作为一个结果，重复请求不得重复入账。
- 原始业务单据、收付款与核销单之间可双向追溯。

## P0 验收

1. 收款可分配到多张应收，部分核销后余额正确；超额核销被拒绝。
2. 已核销收款不能删除或改金额，未核销草稿按权限可操作。
3. 确认收款只更新一次账户余额并生成流水。
4. `DEC-FIN-004` 明确起算日、应付区间和逾期规则后，账龄在模拟日期边界前后进入正确区间。
5. 结转月份的收付款、退款与转账均被拦截。
6. 退款显示原支付方式，改用其他方式时记录原因。

## 原型模拟边界

不接入微信、支付宝、银联、银行或真实打款；支付设置只展示配置流程，所有支付结果标记为模拟。

## ORD-004 到 FIN-001 的应收集成边界

当前状态：`ORD-004` 集成契约为 `ready`，完整 `FIN-001` 页面仍为 `source-only`。用户于 2026-08-14 确认 `DEC-FIN-001/005`：订单级确认发货形成一次应收，金额为订单保存的完整 `orderAmountCents`；不按出库单分摊整单优惠或运费，预收保持占用直至 `FIN-001` 收款/核销，签收不再形成资金结果。

- 资金领域拥有应收事实；订单只能通过公开幂等 command 请求形成应收，不能在订单聚合中复制第二套可编辑应收单。
- command 至少需要 `requestId/orderId/customerId/orderNo/orderAmountCents/occurredAt` 和订单/客户金额快照；在订单级确认发货时调用，客户自提的确认发货同样代表确认交付。
- 发货状态、订单全额应收记录和订单活动日志必须原子成功或失败；资金 provider unavailable/error 时不能先显示已发货再补账。未发货出库作废不碰应收，签收只完成履约。
- `FIN-001` 页面未完成期间可以使用明确标识的确定性 fake adapter 证明调用、幂等和回滚，但不得声称应收列表、收款、核销或资金账户已经实现。
- 差异仅在补发完成或忽略短装后允许发货；“退款”需要 `ORD-005/FIN-004` 的退款单、审核、账户与冲销契约，在此之前只能明确显示不可执行，不能记录“退款成功”或形成虚假应收。

### 筛选与列表

原文没有为资金账户、银行和结转定义关键字等筛选条件，当前不自行添加业务筛选。所有普通列表沿用全局默认 30 条/页和 `createdAt desc,id desc` 稳定排序；月份属于金额口径而非搜索条件，其默认值、URL 与可选范围等待 `DEC-FIN-007`。

资金账户列表：

| 列 | 数据契约 | 显示规则 |
|---|---|---|
| 账户名称 | `name` | 链接详情；空值不允许 |
| 账户类型 | `cash/bank/wechat/alipay` | 分别显示现金、银行账户、微信、支付宝，不增加其他类型 |
| 期初余额 | `openingBalanceCents` | 选择期间期初，整数分格式化；来源受 `DEC-FIN-007/008/010` 约束 |
| 本期收入/支出 | `periodIncomeCents/periodExpenseCents` | 只汇总选择期间的不可变流水；均不得为负 |
| 当前/期末余额 | 计算值 | `期初+本期收入-本期支出`；不得从银行接口读取 |
| 状态 | `enabled/disabled` | 显示启用/停用；停用副作用等待 `DEC-FIN-006` |
| 操作 | 查看明细、编辑 | 无权限或不合法状态不显示假入口 |

账户收支明细按 `occurredAt asc,id asc` 计算同时间稳定余额，页面默认展示选择期间，列固定为日期、账户名称、单据类型、单据号、往来单位、收入、支出、操作后余额和摘要。单条只能有收入或支出一侧大于 0；两者同时为 0 或同时大于 0 都是非法数据。未知/未接入来源显示“来源尚未接入”，不能生成可点击死链接。

账户收支汇总列固定为账户名称、类型、期初、收入、支出和期末。合计基于完整选择期间结果，不只当前页；销售主管若获得只读权限可以查看金额，但银行账号仍受 `DEC-FIN-014` 单独约束。

银行列表列固定为银行名称、账户名称、银行账号、开户行、账户类型、当前余额和状态。当前余额必须取关联资金账户的同一余额投影，不能在银行记录中保存第二份可编辑余额；是否以及如何关联受 `DEC-FIN-012` 约束。

### 表单与校验

账户管理表单的最终可编辑字段和生命周期由 `DEC-FIN-006/008` 决定；规格检查点前只确定以下边界：

- 金额输入解析为整数分，最多两位小数；空值、非数字和超出安全整数拒绝，不用浮点累计。
- 账户类型只允许原文四类；名称、状态与期初不能通过页面临时数组保存。
- 期初余额不是普通资金流水；何时可改、历史如何更正必须等待 `DEC-FIN-008`，不能直接重算已展示流水余额。
- 账户写操作携带 `requestId/expectedUpdatedAt/operatorId/occurredAt`，幂等重放返回原结果，版本冲突要求重新加载。

银行表单固定包含银行名称、账户户名、银行账号、开户行、对公/对私和启用/停用；是否新增/删除、账号唯一性和与资金账户的关联由 `DEC-FIN-012/013` 决定。银行账号按不可信敏感输入处理：页面不得写入 URL、日志或错误详情，输出遮蔽规则等待 `DEC-FIN-014`。

支付通道不接收真实商户号、密钥、证书、银行卡、身份证或支付凭据。开通动作的本地状态和结果等待 `DEC-FIN-015`；无论采用何种方案，界面都必须显示“原型模拟”，不得发起网络请求或改变资金余额。

### 持久化对象与公开边界

最终 schema 名称可以按代码风格调整，但不得省略以下事实：

- `FundAccount`：ID、企业范围、名称、四类账户类型、状态、启用月份、首期期初整数分、创建/更新时间、版本和操作者；不保存可被页面任意覆盖的“当前余额”。
- `FundMovement`：ID、账户、方向、金额整数分、发生时间、来源类型/来源 ID/单号快照、往来单位快照、摘要、操作后余额、requestId 和操作者；确认后不可编辑删除。
- `FinancePeriod`：`YYYY-MM`、状态、各账户期初/收入/支出/期末快照、结转/反结转审计和版本；实际顺序/反结转规则等待 `DEC-FIN-010/011`。
- `BankProfile`：ID、关联关系（等待 `DEC-FIN-012`）、银行/户名/账号/网点/对公私/状态、版本和审计；不复制余额。
- `PaymentChannel` 与模拟申请：固定通道资料、真实开通状态及明确模拟记录；不得保存真实凭据。
- 所有账户聚合和结转请求保留幂等记录；fixture 使用明显虚构银行、账号和摘要。

资金领域未来向 `FIN-001/002/004` 暴露公开 command：校验账户启用、权限、发生月份未锁定、金额和幂等，然后原子追加流水并返回余额；不得允许其他领域直接修改账户 Repository。负余额规则等待 `DEC-FIN-009`，结转门等待 `DEC-FIN-010/011`。查询 provider 必须区分 `available/unavailable/error`，不能把未知余额显示为 0。

### 状态与计算

已由原文固定的计算：

```text
期间期末余额 = 期间期初余额 + 期间收入 - 期间支出
下期初余额 = 已结转上期期末余额
```

- 所有金额为整数分；逐笔操作后余额按确定顺序累计，汇总必须能与最后一笔余额和期间快照对账。
- 只有确认后的未来收款/付款/转账/退款/其他收支才能写资金流水；本切片不把草稿或模拟支付申请计入余额。
- 结转后对应月份的资金写 command 必须在 Service 边界拒绝；不能只在页面禁用按钮。具体首月、顺序、空月和反结转等待 `DEC-FIN-010/011`。
- 账户停用不等于余额归零或删除历史；最终能否带余额停用和恢复等待 `DEC-FIN-006`。
- 当前只支持一种账面币种还是需要币种字段，原文没有给多币种或汇率；本切片不增加多币种换算。若后续出现真实多币种需求，必须新建决策而不能重解释现有金额。

### 权限与字段遮蔽

原文已给细权限候选：查看资金账户、管理资金账户、查看账户收支、管理银行列表、管理在线支付。结转缺少独立权限，销售主管只读范围和银行账号遮蔽也不完整，因此最终 baseline 由 `DEC-FIN-014/016` 决定。

- 路由、UI、Runtime/Store、Service command 和导出（若后续加入）必须消费同一权限结果。
- 直接调用 Service 越权时拒绝；页面隐藏按钮不能代替命令授权。
- 银行账号、未来支付凭据和内部诊断信息不得出现在普通日志、错误或 URL。
- 本切片不因为财务可管理账户就自动赋予订单、库存、设置或真实支付权限。

### 页面状态与 Mock

单一 baseline 至少准备：现金、银行、微信/支付宝账户类型；启用/停用状态；有期初和多笔收入/支出的期间；一个已结转月和当前未结转月；关联银行资料；未开通支付通道。所有名称、账号、单号和往来单位均为明显虚构数据，并与未来切片来源明确区分。

| 场景 | 可见表现 | 数据结果/恢复 |
|---|---|---|
| `normal` | 账户、流水、汇总、结转、银行、支付介绍可达 | 余额和期间快照一致，写动作按确认契约执行 |
| `empty` | 各页显示成功空状态；无账户时不能结转 | 返回 normal 或清空筛选可恢复 |
| `error` | Repository/写入失败显示可理解错误和重试 | 不留半账户、半结转、半银行或余额变化 |
| `slow` | 提交中禁重复，旧响应不覆盖新版本 | 同 requestId 最多生效一次 |
| `permission-denied` | 无权限角色被路由拒绝且无写入口 | 直接 Service 调用同样拒绝 |
| `partial-failure` | 银行/支付资料失败不抹去账户汇总；余额/期间 provider 失败阻断相关动作 | unavailable/error 不显示 0 或已开通 |
| `boundary` | 金额两位小数、重名、非法类型、锁定月、未来月、停用账户、账号边界 | 校验失败前后状态哈希一致 |
| `concurrent` | 两会话编辑同账户或同时结转/反结转 | 首个成功，后续 `CONFLICT` 并重新加载 |
