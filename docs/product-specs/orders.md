# 订单领域规格

## 需求来源与事实边界

- 直接业务来源：[02-订单模块.md](../references/requirements/02-订单模块.md)；全局交互与角色资料来自 [01-整体架构与首页.md](../references/requirements/01-整体架构与首页.md) §4～§5。
- 功能切片、原文章节、依赖、规则归属和字段准备度以 [产品规格索引](index.md) 为唯一目录。
- `ORD-01～ORD-15` 直接整理自原文 §8。分层、整数分、原子提交、Mock 场景属于 Harness 工程约束，不表示原文已定义技术实现。
- 对应切片为 `source-only` 时只能提取契约；订单标签、库存预占、特价审批、预收占用、应收时点和退款跨域结果按索引中的人工决策门处理。

## 目标与范围

覆盖客户订单、客户退单、差异单、销售出库单、订单/销售统计。原型 P0 黄金旅程是“新增订单 → 审核 → 部分/全部出库 → 应收与收款记录”。

## 主要页面

- 订单：列表、筛选/批量操作、新增、详情、分享。
- 退单：列表、新增、详情与退款状态。
- 差异单：列表与详情。
- 销售出库：列表、详情、作废后重新出库。
- 统计：商品明细/汇总、客户汇总、出入库明细/汇总。

## 核心状态

正常销售状态单向推进；需求明确允许的例外仅为“待财务审核 → 待订单审核”。实现时状态枚举、允许动作和操作者权限必须位于 service/config，不散落在按钮判断中。

## 业务规则

| ID | 必须行为 |
|---|---|
| ORD-01 | 单号按“前缀 + YYMMDD + 序号”自动生成且不可编辑。 |
| ORD-02 | 正常状态不可回退；仅允许待财务审核回到待订单审核。 |
| ORD-03 | 实出小于应出时自动生成关联差异单。 |
| ORD-04 | 整单退和部分退均关联原订单。 |
| ORD-05 | 可退数量不得超过已出库数量。 |
| ORD-06 | 退款必须经过确认退款流程。 |
| ORD-07 | 确认出库时实时扣减可用库存。 |
| ORD-08 | 选择客户与商品后自动匹配客户等级价格。 |
| ORD-09 | 客户只能订购已授权商品。 |
| ORD-10 | 分享链接超过有效期后不可查看或确认。 |
| ORD-11 | 下单时自动占用客户预收金额。 |
| ORD-12 | 特价订单必须标记并进入特殊审批。 |
| ORD-13 | 作废出库单保留可查，并支持重新出库。 |
| ORD-14 | 订单自定义属性来源于设置配置。 |
| ORD-15 | 统计二维表支持配置展示维度。 |

## 跨领域约束

- 下单读取客户状态、商品授权和价格；任何校验失败都不能生成半成品订单。
- 确认出库与库存扣减是一个业务结果；失败时两者都不生效。
- 出库/签收形成应收的具体时点需按资金规格；未确认前不得自行决定。
- 原始需求没有库存预占规则；不得因为系统通常会预占库存而自行实现。
- `ORD-11` 按已确认 `DEC-ORD-004` 自动占用 `min(当前可用预收,订单金额)`；修改按旧占用原子增占/释放差额，退回不释放，取消/删除/作废未履约订单释放。
- 金额使用整数分，优惠、运费、预收占用和应收之间必须有可追溯明细。

## 实现映射

`src/features/orders/` 保存订单类型、repository、状态机 service、stores 和页面；库存、商品、客户、资金能力通过公开 provider 注入。

## P0 验收

1. 按客户、日期、单号、状态筛选订单，列表/分页/空结果正确。
2. 已授权商品带入正确价格优先级，未授权商品不可提交且说明原因。
3. 新订单单号不可修改，金额汇总以分计算并正确格式化。
4. 状态按允许路径推进；非法回退被 service 拒绝而非仅隐藏按钮。
5. 部分出库同时扣正确库存并生成差异单；库存不足整体失败。
6. 退货数量超过已出库数量被拒绝；退款需确认。
7. normal/error/slow/permission-denied 场景和订单黄金旅程测试通过。

## 原型模拟边界

分享、打印、导入导出、物流与收款通道只模拟结果。统计先用固定数据验证信息结构，未定义的指标口径不得声称真实准确。

### 表单与校验

`ORD-001` 没有新增/修改业务表单，只有查询、导出和模拟打印输入：

- 查询 Schema 对页码、枚举、日期顺序和金额顺序做运行时校验；金额文本按两位小数安全转整数分，不接受 `NaN`、负数或超出安全整数范围。
- `orderId`、选择集合和打印目标必须在 service 中重新校验存在性、可见性与权限；不能只靠路由或按钮隐藏。
- 导出只接收已经归一化的查询或选中 ID；服务端式 adapter 再执行相同数据范围和字段遮蔽，不信任前端列配置。
- 模拟打印必须先打开预览，用户确认后才提交一次打印命令；取消预览没有写入。计数、操作日志和结果必须原子提交，规则由 `DEC-ORD-012` 决定。
- 详情中的修改开票信息、添加备注、添加附件、新增、修改、复制、退回、删除、作废、分享、收款、出库和发货均不是本切片表单，不得提前保存半成品数据。

只读聚合最小模型如下；字段名称是领域契约，不要求 UI 原样显示英文：

| 聚合部分 | 必需字段 | 约束 |
|---|---|---|
| 订单头 | `id, orderNo, status, orderedAt, createdAt, updatedAt` | `id/orderNo` 企业内唯一；时间为 ISO 字符串并由受控时钟解释 |
| 人员快照 | `salespersonSnapshot{id,name}, creatorSnapshot{id,name}` | 保留当时显示名，不反向编辑组织资料 |

### 详情与操作矩阵

基础信息必须显示状态、客户、单号、客户编码、结算方式、业务员、制单人和下单时间。应收额度读取客户当前 provider；应收总额和可用预收读取资金 provider；本单占用预收受 `DEC-ORD-004` 约束。不得从订单金额反推；未实现显示“数据源尚未接入”，失败显示“加载失败”并允许单区块重试，不能显示 0。

订单详情 Tab 按下列分区展示：

1. 商品明细：序号、商品图片/名称/编码、规格、数量、单位、折扣、成交单价/原价、金额小计、重量小计和原因；“库荐”整列明确显示算法未接入，不从库存猜算；规格 1/2/3 不展示且不建字段。
2. 金额汇总：原价金额、商品优惠（含赠品）、整单优惠、运费和订单金额；遮蔽权限与列表一致。
3. 收货信息：交货日期、配送方式、收货人/电话、详细地址和发货仓库。
4. 开票信息：不开票/待开票/已开票及现有抬头快照；本切片只读。
5. 自定义属性：显示下单时保存的定义和值快照；不根据不存在的设置配置生成字段。
6. 备注、附件和操作日志：只读展示已有资料；系统日志详情不在本切片伪造。

### 状态与计算

- 本切片只展示状态，不提供任何状态迁移命令。状态枚举必须由 service/config 单点拥有，列表、详情、筛选和时间轴复用同一映射。
- 规范状态仅八个：`pending-order-review`（待订单审核）、`pending-finance-review`（待财务审核）、`approved`（已审核/待出库）、`outbound-in-progress`（出库中）、`outbound`（已出库/待发货）、`shipped`（已发货/待签收）、`completed`（已完成）、`canceled`（已取消）。别名只用于中文提示，不建立重复枚举。
- 详情四段时间轴为只读投影：审核、出库、发货、完成；当前状态映射到阶段，取消状态单独显示终止原因/时间（若快照存在）。不得用时间轴点击推进状态。
- 金额全部使用整数分：`orderAmountCents = originalAmountCents + productDiscountCents + orderDiscountCents + freightCents`。两类优惠必须小于等于 0，运费大于等于 0；不满足等式的订单 Schema 拒绝载入，不能在 UI 静默修正。
- 行小计是保存的成交快照并以整数分显示；`ORD-001` 不重新执行价格、授权、促销或单位换算。折扣显示值来自 `discountBasisPoints`，`10000` 表示 100%。
- 打印次数是非负整数；只有确认打印命令成功才增加。出库打印、差异标记和物流编码是只读履约投影，当前切片不计算。
- 订单、列表结果、导出和打印均遵守企业隔离、软删除和角色可见性；不存在或不可见的订单对外统一为未找到，避免泄露 ID。

### 表单与校验

单笔状态命令统一使用下列最小输入；未知字段拒绝，所有 ID 和文本去首尾空格后校验：

| 字段 | 类型 | 必填 | 规则/用途 |
|---|---|---|---|
| `orderId` | ID | 是 | Service 重新校验企业、未删除、可见性和当前状态 |
| `action` | enum | 是 | 固定为 `approve-order`、`return-order`、`approve-finance`、`return-finance`、`cancel-order` |
| `expectedUpdatedAt` | ISO datetime | 是 | 与最新订单版本严格一致，否则 `CONFLICT`，不能覆盖其他审核/编辑结果 |
| `requestId` | 非空 string | 是 | 同一请求只产生一次状态、审核记录、资金/分享副作用和日志 |
| `reason` | string/null | 条件必填 | 退回/取消必填 1～200 字；审核通过可选备注，最多 200 字且不替代确认 |

批量业务审核输入为 `items[{orderId,expectedUpdatedAt}] + requestId`；ID 不得重复且至少一项，固定限制当前页最多 100 条。只支持业务审核通过，不支持批量财务审核、退回或取消。

订单聚合需要保留审核历史，而不能只改当前状态：

| 字段 | 类型 | 说明 |
|---|---|---|
| `reviewRound` | 正整数 | 首次保存为 1；任一退回后首次成功编辑递增，同一轮内继续编辑不重复递增 |
| `reviewRecords[]` | immutable records | 已发生的每次审批/退回/取消记录，不因再次编辑删除 |
| `reviewRecords[].stage` | `order` / `finance` | 特价审批合并在 finance stage，以 `specialPrice=true` 和依据快照区分，不建立独立状态/阶段 |
| `reviewRecords[].outcome` | `approved` / `returned` / `canceled` | 必须与命令和 from/to 状态一致 |
| `reviewRecords[].actorSnapshot` | `{id,name,role}` | 保存当时操作者，不跟随员工改名 |
| `reviewRecords[].reason` | string/null | 退回/取消原因及可选通过备注，不记录敏感财务详情 |
| `reviewRecords[].fromStatus/toStatus` | `OrderStatus` | 即使业务退回保持同一规范状态，也能审计动作结果 |
| `reviewRecords[].occurredAt/requestId` | datetime/string | 受控时钟；请求 ID 仅用于幂等和诊断，不在普通 UI 暴露 |

特价订单必须保存可靠的历史依据：补充 `specialPriceReason`，人工勾选或价格越界时均必填 1～200 字；保存时生成 `specialPriceEvidence[]`，逐条保存异常行 ID、SKU/单位快照、成交价、当时最低/最高售价及越界方向。越界时特价标记不可取消，恢复到界内后可取消；仅人工标记且没有越界行时证据数组可空，但原因仍必填。财务审批不得用后来变化的商品价格反算历史原因。已有 fixture 通过显式 schema migration/基线升级补齐，不在读取时默默虚构。

### 状态与计算

原文明示且当前可固定的状态主链如下；所有判断必须位于同一状态机配置并由 Service 强制执行：

| 当前状态 | 动作 | 成功状态 | 明确副作用 | 尚待决策 |
|---|---|---|---|---|
| `pending-order-review` | 业务审核通过 | `pending-finance-review` | 原子写审核记录、活动日志和 `updatedAt`；特价订单不增加新状态 | 销售主管/管理员且有 `orders.review` |
| `pending-order-review` | 业务退回 | `pending-order-review` | 必填原因，记录“已退回待修改”；不释放预收、不改库存 | 销售主管/管理员且有 `orders.return` |
| `pending-order-review` | 取消 | `canceled` | 必填原因，原子释放本单预收、撤销有效分享；不扣/补库存且不可恢复 | 销售主管/管理员且有 `orders.cancel` |
| `pending-finance-review` | 财务审核通过 | `approved` | 原子写审核记录、日志和 `updatedAt`；特价时要求强化确认 | 财务/管理员且有 `orders.finance-review` |
| `pending-finance-review` | 财务退回 | `pending-order-review` | 必填原因，保留预收占用和全部历史；之后允许按 `ORD-002` 修改 | 财务/管理员且有 `orders.return` |

- `approved` 及以后状态在本切片没有退回、取消、编辑、出库或资金写命令。非法状态即使绕过按钮直接调用 Service 也必须拒绝。
- 普通审核通过不得预占/扣减库存，也不得生成出库单、差异单、物流、应收或收款；这由 `DEC-ORD-002` 与切片边界固定。
- 审核只消费已保存且通过 Schema 的订单、预收占用和特价依据；不得重新读取当前客户/仓库/信用来改变审批结果，不重新计算订单金额、折扣、价格、授权、单位或收货快照，不调整预收、不形成应收。
- 每个成功命令只产生一条领域审核记录和对应安全活动日志；幂等重放返回原结果，不重复写。失败必须保持订单、审核记录、预收、分享和日志的事务前状态。
- 列表、详情和时间轴从状态机/审核历史投影，不从按钮是否显示反推业务状态。财务退回后要显示退回原因和历史已通过的业务审核，但当前主状态仍是待订单审核。

### 表单与校验

待出库表格逐行消费订单保存快照和库存实时 provider：

| 字段 | 类型/来源 | 规则 |
|---|---|---|
| `orderId/expectedUpdatedAt` | ID + ISO datetime | 重新校验企业、可见性、`approved/outbound-in-progress` 和乐观版本 |
| `warehouseId` | 库存 provider | 默认计划仓，可选任一启用且非禁售仓；订单允许多次多仓，提交时重验 |
| `orderLineId` | 订单行 ID | 只能选择当前订单仍有待出数量的销售/赠品行 |
| 商品/规格/单位 | 订单快照 | 不读取当前商品改写历史；单位继续显示订单单位 |
| 库位/批次 | FIFO 预览 | 只读展示库存 command 的真实分配，不能由 UI 手改或选择过期批次 |
| 库存数量 | 库存 provider | 展示当前账面库存与 FIFO 可出量；在途/预购明确 unavailable，不按 0 相加 |
| 订货/已出/待出数量 | 基本单位千分定点 + 订单单位格式化 | `待出=订货-全部未作废实出`，不得为负 |
| 本次出库数量 | 订单保存单位正整数，默认待出 | 换算为基本单位千分量，累计不得超订单行；只有全部行为 0 且结束剩余时才允许不建出库单 |
| 单价/金额 | 订单成交快照 | 行金额=本次数量×保存成交单价，赠品为 0；不重新定价、不分摊整单优惠和运费 |
| `finishShort/reason` | 条件字段 | 计划分批不建差异；显式结束剩余时原因必填 1～200 字，并为全部剩余只建一张待确认差异 |
| `requestId/operatorId/occurredAt` | command 元数据 | 幂等、审计和受控时钟；普通 UI 不显示 request ID |

最小持久化对象不得只改订单状态：

- `SalesOutbound`：`id/outboundNo/orderId/status/warehouseSnapshot/customerSnapshot/confirmedAt/operatorSnapshot/documentAmountCents/lines/printRecords/voidInfo/version`。
- `SalesOutboundLine`：订单行、SKU/名称/规格/订单单位快照、订货/本次实出基本数量、成交价/金额/重量及 `allocations[]`。
- `allocations[]`：库存 movement、库位、批次、生产/有效日期和基本数量快照，支持精确作废冲销。
- `OrderFulfillmentProjection`：累计有效出库数量、出库单数/打印次数、物流编码、差异标记和最近履约时间；全部从真实履约记录投影，不手工维护第二套事实。
- `ShipmentRecord`：每订单最多一条，关联全部有效出库单；物流配送编码必填 1～80 字，送货上门可选，客户自提不填编码。
- `ReceiptRecord`：每订单最多一条成功记录，含签收时间、1～80 字签收人、≤500 字备注；无记录即未签收。
- `DifferenceDocument`：显式结束剩余时创建一张；保存 `pending-confirmation/confirmed/voided`、差异行、原因及 `reship/ignore` 结果，`refund` 仅为不可执行占位。
- 出库、作废、发货、签收、差异确认和打印均保存请求记录，幂等重放返回原结果且不重复库存/资金/日志副作用。

### 状态与计算

已由原文和既有八状态固定的主链只有：

```text
approved → outbound-in-progress → outbound → shipped → completed
```

- 首次有效部分出库后进入 `outbound-in-progress`；累计有效实出达到订单数量后进入 `outbound`。一步全部出库可由 `approved` 直接进入 `outbound`。
- 出库累计只计算未作废记录；赠品同样扣库存但成交价和金额保持 0。累计实出不得超过订单行基本数量。
- 每次提交先对全部行取得 FIFO 预览，再在一个跨领域协调事务中完成所有库存扣减、出库单、订单状态/投影和日志；任一行库存不足、仓库不可用、盘点/结转锁定、版本冲突或写入失败时全部不生效。
- 现有库存单 SKU command 必须扩展为可由订单协调器一次确认多行并返回完整 allocations；订单不能循环提交后自行补偿。库存仍拥有余额、批次、库位和流水，订单只保存不可变分配快照。
- 盘点和结转实体属于 `INV-003`，但 `INV-06/14` 是明确规则；本切片只能通过库存公开操作门读取 `available/locked/unavailable`。锁定时拒绝，门禁自身失败时不得假定“未锁定”。
- 出库不重验当前客户状态、价格、授权、订单金额或审核结果；只校验当前订单状态/版本、实际仓库与库存操作门。确认发货时以完整 `orderAmountCents` 幂等形成一次订单级应收，预收保持占用；签收不再产生资金副作用。
- 只有全部实出或短装差异已忽略时才能由 `outbound` 一次发货；补发把订单按有效实出量重开为 `approved/outbound-in-progress`；退款分支阻断。仅 `shipped` 可签收，签收时间不得早于发货或晚于当前，成功进入 `completed`。

### 详情与操作矩阵

| 能力 | 原文已知字段/行为 | 已确认实现结论 |
|---|---|---|
| 出库作废 | 作废单号、时间、仓库、原因及原出库行/批次/金额保留，可重新出库 | 仅未发货 confirmed 单可因 1～200 字原因作废；按原 allocations 精确恢复并写反向流水，保留原单、作废未处理关联差异并重算状态 |

| 确认签收 | 签收时间、签收人、已/未签收、备注；完成后订单 `completed` | 每单只存一次成功签收；仅 shipped、时间合法、签收人及备注合法时进入 completed；拒收/部分签收不在本切片 |
| 差异单 | 单号、订单/客户/仓库/时间、订单/实出/差异数量和金额、原因、待/已确认、补发/退款/忽略 | 仅显式短装结案生成；补发重开履约、忽略允许发货、退款保持不可执行；作废关联出库时同步作废未处理差异 |

### 权限与字段遮蔽

细权限区分 `orders.outbound`、`orders.void-outbound`、`orders.ship`、`orders.confirm-receipt`、`orders.view-difference`、`orders.confirm-difference`、`orders.print-outbound`。管理员拥有全部；仓库默认拥有出库/作废/发货/打印/签收；销售主管默认查看履约、查看/确认差异和签收；业务员默认查看本人可见订单履约及签收；财务仅只读金额/应收。以下既有边界不因新页面改变：

- 仓库角色可见履约所需客户/收货/商品/数量/仓库/批次，但订单成交价、折扣、应收、预收、出库金额继续遮蔽。
- 财务角色只读客户/结算/金额/发票和资金结果，收货电话、详细地址、批次库位和物流细节继续遮蔽。
- 销售角色不能因能查看订单就自动获得库存扣减、作废或发货权限；所有写动作由独立权限控制。
- 路由、按钮、Store/Runtime、Service 和打印输出使用同一能力结果；直接调用 Service 越权时统一拒绝且不泄露不可见单据。

| `FIN-001/003` passing | Finance 拥有不可变应收、收款/核销/预收、账户流水和期间锁 | 退货调整与退款实体尚不存在，不能直接改余额或删除核销 |
| `INV-001` passing | Inventory 拥有基本单位余额、批次/库位、成本快照、幂等入库 command 和不可变流水 | Order 不得直接增加库存或借退货实现通用其他入库页面 |

本切片的业务边界是客户退货闭环。订单继续拥有退单申请、审核和三重状态投影；Inventory 只通过公开 command 接收退货入库；Finance 只通过公开 command生成应收贷项、退款义务、退款单、账户支出或预收恢复。任一跨域写失败必须恢复三个领域到提交前状态。

### 三重状态与操作

原文明确三条独立维度，但没有完整转换：

- 退单状态候选：原文 `待审核/已审核/已完成/已取消`，设置另有“退回退单”和“作废退单”。是否增加 `returned`、作废和取消关系由 `DEC-ORD-047` 决定。
- 收货状态：原文只有 `未收货/已收货`。是否支持部分收货、入库作废后恢复和差异由 `DEC-ORD-048/INV-015` 决定。
- 退款状态：订单只给 `未退款/已退款`，资金给 `待审核/已退款/已拒绝`。Order 只能保存 Finance 状态投影，统一枚举和重新申请受 `DEC-FIN-031/034/036` 决定。

在决策前唯一安全顺序是：创建退单不能动库存或资金；审核前不能入库；未完成规定入库前不能确认普通退货退款；退款必须显式确认。不得把按钮点击、页面跳转或“已审核”直接等同于库存增加或退款成功。

### 金额、应收与退款守恒

既有不可变事实：订单发货形成一次完整原应收；收款、优惠核销、预收与账户流水不可由退单页面重写；资金结转月禁止新增资金出入；账户不得为负。`ORD-005` 必须新增可追溯调整而不是修改历史。

本轮需固定以下公式，当前仅作为决策候选：

```text
退货商品毛额 = Σ(退回数量 × 原订单保存成交单价)
可退业务净额 = 退货商品毛额 - 可追溯的退回行折扣分摊 + 经确认的运费调整
应收贷项 = min(可退业务净额, 该订单当前待收 + 该订单已核销的可调整金额)
退款义务 = max(0, 应收贷项 - 调整前订单待收)
现金实退 + 余额恢复 = 退款义务 - 不可退款优惠份额
```

这些公式中的折扣/运费分摊、优惠份额、来源顺序和短装差异必须由 `DEC-ORD-044`、`DEC-FIN-003/032～035` 明确，不能直接编码。任何最终公式都必须满足：调整后应收不小于 0；累计贷项不超过原应收；累计实退不超过可追溯真实收款/预收消费；优惠不会变成现金；同一退单/来源不会重复退款。

### 退货入库边界

Inventory 仍是唯一库存 owner。退货入库至少需要来源退单、退货仓库、启用库位、SKU、基本单位数量、批次/生产/有效期、成本、操作人、时间和 requestId；成功追加 `customer-return-inbound` 不可变流水并返回 movement 引用。Order 在同一协调事务中写入库投影和收货状态，任一行失败全部回滚。

原文只支持已/未收货，且通用其他入库页尚未实现。一次或多次入库、原批次或新批次、成本、错单作废和退款后纠错分别受 `DEC-ORD-048`、`DEC-INV-014/015`。在决定前不得把审核通过自动当成库存入库，也不得让 Order 直接修改 Inventory fixture。

### 退款与短装差异边界

Finance 必须成为退款调整、退款义务、资金支出和余额恢复的唯一 owner。确认退款需要校验退单审核/收货前置、退款剩余上限、来源分配、账户状态和余额、期间、日期、版本与 requestId，并与 Order 状态投影原子提交。真实微信/支付宝/银联原路退款不在浏览器原型中；若采用 fake adapter，界面必须明确“原型模拟”，底层仍只能修改确定性 Mock。

ORD-004 短装差异退款没有商品退回，不能复用普通退货入库。它是否创建独立退款请求、何时允许发货、完整原应收如何追加贷项以及未收款时是否只有应收调整，统一由 `DEC-ORD-051` 和 `DEC-FIN-003/032` 决定；确认前现有禁用入口保持正确行为。
