## 目标

在不改变 PDF 推荐目录层级的前提下，检查并补齐 AI 实现蜂订系统时需要的功能范围、需求来源、依赖顺序、字段提取方法、未知问题处理、人工决策点和验收证据，尽可能消除依靠聊天记忆、竞品习惯或模型常识补全业务的空间。

## 范围与非目标

范围包括八份原始需求、八领域产品规格、总体实施顺序、质量状态、执行计划规则、可靠性、安全规则和 Harness 自动验证。本计划不实现新的业务页面，不改变 Vue 应用视觉，不接入真实后端或第三方服务。

## 事实来源

- `AGENTS.md`、`ARCHITECTURE.md` 与 `docs/` 当前 Harness。
- `docs/references/requirements/` 中八份逐字需求快照及哈希清单。
- Git 历史中迁移前的 46 项功能拆分，仅作为待核对的候选目录，不直接当作当前事实。
- 《Harness Engineering 学习指南》第 101 页以后关于短入口、深链接、执行计划、质量、可靠性与机械约束的职责划分。

## 前置门禁

- 当前工作区在计划创建前为空，Harness 基线通过。
- 本计划只修改 Harness 文档与机械验证，不改变业务界面和业务行为。
- 迁移前功能清单只作为审计线索，所有内容必须能回指当前需求快照。

## 验证路径

- 追踪验证：每个业务切片具有稳定 ID、所属领域、原始需求文件/章节、依赖、优先级和产品规格入口。
- 防幻觉验证：缺来源、缺依赖、重复 ID、未知状态、未决问题无负责人或无阻塞范围时机械失败。
- 文档验证：入口链接可达，官方目录外不新增重复治理入口，所有产品规格声明来源和字段准备状态。
- 自动回归：`npm run verify:harness`、`npm run typecheck`、`npm run test:run`、`npm run build`。

## 风险与阻塞

- 原始需求内容很多，不能把目录标题误当成已经确认的字段或规则。
- 原迁移前功能清单可能包含助手的拆分判断，必须回到原始需求核对覆盖和章节。
- 同一事实不得同时在多个文件维护可变状态；目录、顺序、状态和执行现场要各有唯一职责。
- 需求本身含糊或冲突的内容必须显式登记并设置人工决策门，不能为追求“完整”而补造答案。
