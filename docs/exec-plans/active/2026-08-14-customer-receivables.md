## 目标

从资金、订单、客户、权限原文和既有 `ORD-004`、`FIN-003` 公开边界提取客户应收、收款单与收款核销的完整可编码契约。明确应收唯一所有者、收款入账、预收占用、优惠、核销/取消、账龄、编号、权限和原型附件边界；在全部阻塞决策写回且 `FIN-001` 达到 `ready` 前，不创建 FIN-001 业务代码、页面或 fixture。

## 范围与非目标

本切片只覆盖 `FIN-001`：客户应收汇总、按单据/商品明细、应收账龄、收款单列表/新增/详情、收款核销单列表/新增/详情/取消，以及订单详情“收款记录”接入。应收形成沿用 `DEC-FIN-001/005`：订单确认发货时按订单完整金额只形成一次。

供应商应付/付款属于 `FIN-002`；客户退单、退款、转账和其他收支属于 `ORD-005/FIN-004`；机构收款与全局资金统计属于 `FIN-005`。本切片不接真实支付、真实文件上传或银行接口，不修改已确认的发货形成时点，也不以收款页面伪造退款、应付或统计结果。

## 风险与阻塞

- `ORD-004` 当前在订单状态内保留临时应收投影；`FIN-001` 必须明确 canonical owner 和新发货的原子接入，不能留下两套可变应收余额。
- 原文同时出现“收款金额”“优惠金额”“余额支付”“立即核销”和独立多单核销，但没有说明剩余款是否成为预收、优惠如何冲应收或多对多分配方式。
- 收款表单只说银行转账时账户必填，却又要求每笔收款实时更新资金账户；现金、微信、支付宝和余额的账户副作用冲突。
- 原文提供收款作废、核销取消和 FIN-04，却没有说明部分核销后的作废、取消恢复预收/占用、历史已结转月份和不可变流水处理。
- 账龄区间从 1 天开始，未定义当日应收、账龄起算、月结到期日和逾期；按商品明细也未定义部分核销如何落到 SKU。
- 全局资金只读和设置细权限没有给五角色在应收、收款、核销及联系人/电话上的完整映射。

## 已确认方案（2026-08-14）

| 决策 | 推荐方案 | 主要理由 |
|---|---|---|
| `DEC-FIN-004` | 以 Asia/Shanghai 本地自然日计算：形成日为第 0 天，首桶显示 `0～30天`，其余沿用原文区间；年龄只对待收金额分桶。现结到期日=形成日，账期=形成日+快照天数，月结=形成月最后一日；当前本地日期晚于到期日且仍待收才逾期。客户汇总“账期天数”取最老未结应收年龄，“最后收款日期”取最后有效核销日期。 | 覆盖原文遗漏的当日且保证账龄合计不丢金额，同时把年龄与是否逾期分开解释。 |
| `DEC-FIN-017` | Finance 成为 `CustomerReceivable` 唯一 owner；订单发货通过 Finance `public.ts` 原子创建应收，订单详情只读 Finance 投影。应收保存订单/客户/联系人/商品/金额/结算方式和账期快照；现有 Order 临时投影迁入 Finance 后不再维护可变余额。 | 避免 Order 与 Finance 两套应收金额漂移，并保持来源快照可追溯。 |
| `DEC-FIN-018` | 已形成应收不可编辑、删除或随订单资料重算；状态由有效核销派生为 `open/partial/settled`。退货、退款、差异和错账更正必须等待 `ORD-005/FIN-004` 的可追溯调整单。 | 已发货事实不能被页面静默改写，后续冲销需要独立证据。 |
| `DEC-FIN-019` | 新增收款“保存”即确认，原子创建 `normal` 收款和必要账户收入，无草稿/审核；允许为已停用/冻结客户收历史欠款。收款金额、方式、账户确认后不可编辑，不物理删除，只能按 `DEC-FIN-024` 作废。 | 对齐 FIN-03 的实时余额并避免出现未定义的草稿/审核状态。 |
| `DEC-FIN-020` | 现金/银行转账/微信/支付宝分别必须选择启用的同类型 FIN-003 账户；银行账户还须有启用银行资料。`余额`表示使用客户预收，不产生新收款资金流水，也不选择资金账户；原文线上链支付保持明确 unavailable。 | 每笔真实入账都有唯一账户，余额消费不会伪造第二次现金流。 |
| `DEC-FIN-021` | 正常收款未分配现金自动进入客户可用预收，允许收款超过当前应收；订单已占用预收保持绑定该订单。核销时可消费该订单占用预收或客户可用预收；取消订单沿用既有规则释放，取消核销恢复原占用（订单仍有效）或可用预收。所有变化使用不可变预收账。 | 把既有订单预收占用接成闭环，同时保持可用+占用+已用金额守恒。 |
| `DEC-FIN-022` | 核销采用同一客户的手工多对多分配矩阵，每行明确来源收款/预收、目标应收和金额；不自动 FIFO。一张核销单可部分或全额匹配多张来源/应收。立即核销默认否，开启时复用同一分配命令并与收款原子提交。 | 手工归属可审计，不用模型猜测财务希望冲哪一张单。 |
| `DEC-FIN-023` | 订单收款允许手工优惠，必须填写备注；分配行保存 `cashCents/discountCents`，两者合计冲减应收，只有 cash 消耗收款并移动账户。优惠不得超过目标待收；“计算优惠”显示规则未配置，不自动给数。核销单同时展示现金和优惠拆分。 | 保留原文字段但不编造优惠公式，也不把优惠伪造成到账资金。 |
| `DEC-FIN-024` | 仅当前开放自然月、没有任何有效核销的 normal 收款可作废，原因 1～200 字；追加同账户反向流水并保留原单/审计。核销只能整张取消，原因必填；恢复应收、收款和预收来源，不再次移动现金；有后续依赖或版本冲突时拒绝。 | 避免跨已结转期间改账和级联重算，同时保留可恢复的纠错路径。 |
| `DEC-FIN-025` | 商品行不做无来源的按比例分摊；每行继承所属应收单的 `待收/部分收款/已收` 三态。只有整张应收结清时全部商品显示已收。 | 如实表达文档级核销，不制造 SKU 级现金归属。 |
| `DEC-FIN-026` | 企业内按业务发生日分别生成 `YS-YYMMDD-#####`、`SK-YYMMDD-#####`、`HX-YYMMDD-#####`，日序列从 00001 递增、并发唯一、作废/取消后不复用。 | 三类单号可肉眼区分并稳定追溯，规则与既有差异单日序列一致。 |
| `DEC-FIN-027` | 全部日期使用 Asia/Shanghai 受控时钟且不得晚于当前。收款月份必须未结转，且发生时间不得早于所选账户最新流水；核销日期不得早于任何所选应收/收款/预收来源日期。requestId 幂等、聚合版本冲突后刷新重试。 | 保护 FIN-003 不可变逐笔余额、期间锁和账龄时间顺序。 |
| `DEC-FIN-028` | 细权限采用规格中的八项：管理员/财务全量；销售主管拥有应收/明细/账龄、收款/核销列表与详情只读和应收导出，无新增/作废/取消；业务员、仓库无 FIN-001 权限。订单 Tab 仍按订单可见范围，但新增收款只对管理员/财务显示。四层一致。 | 对齐“销售主管资金只读”和设置细权限，同时不扩大资金写权限。 |
| `DEC-FIN-029` | 管理员/财务在应收业务页可见形成时联系人和完整电话；销售主管可见联系人但电话按 `前三位****后四位` 遮蔽，导出沿用同样结果；业务员/仓库无入口。日志、URL、错误永不记录完整电话。 | 财务具备联系付款方的必要资料，又不因销售主管只读而扩大敏感信息。 |
| `DEC-FIN-030` | 收款凭证只允许 0 或 1 个 pdf/jpg/png、≤5MB；原型只保存明显虚构的文件名、MIME、大小和 fake ID，不读取、上传、预览真实内容或本地路径。 | 覆盖原文字段并遵守原型安全边界，避免真实文件外传。 |
