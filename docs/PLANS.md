# 执行计划

执行计划保存跨会话工作现场，使下一位 AI 只依赖仓库就能继续，不依赖聊天记录，也不能借“先做再说”绕过产品规格。

## 何时必须建立计划

- 任一业务功能切片，无论页面大小。
- 工作会跨会话、影响多个步骤、状态流转、数据契约或架构边界。
- 验证、迁移、外部能力或回退风险较高。
- 存在尚未决定、会改变用户行为或数据结果的问题。

纯文字修正或不改变行为的局部样式修复可以不建计划，但仍需运行相关验证并同步事实文档。

## 位置与唯一现场

- 进行中：`docs/exec-plans/active/YYYY-MM-DD-short-topic.md`
- 已完成：`docs/exec-plans/completed/YYYY-MM-DD-short-topic.md`
- 已确认但有意延期的工程问题：`docs/exec-plans/tech-debt-tracker.md`

同一时间最多一个业务 active plan。产品规格索引记录“有什么、能否提取规格、是否达到编码门”，总体顺序记录“先后关系”，active plan 只记录“当前怎么做和做到哪里”，质量评分只记录“哪些结果已有证据”。

## 计划头信息

每份计划必须包含：

```markdown
- 类型：business-feature | harness | architecture | maintenance
- 功能：CUS-001                 # 非业务计划写“不适用”
- 当前阶段：specification       # specification | implementation | verification | audit
- 状态：active
- 最近更新：YYYY-MM-DD
```

业务计划的功能 ID 必须存在于 `product-specs/index.md`。一个计划不得混合多个业务切片；真正不可拆分的跨域事务需要先在设计文档说明，并仍指定一个主切片。

## 业务阶段门禁

### specification

允许阅读原始资料、建立字段与交互契约、记录人工决策、准备验收和 Mock 契约；不得开始业务实现。计划必须引用精确产品规格、原始文件和章节，不能只写“相关需求”。

### implementation

只有在以下条件全部满足后才能进入：

- 产品规格索引中的字段准备度为 `ready`。
- 对应领域规格存在完整的“`<功能ID> 字段与交互契约`”。
- 依赖切片均有 passing 证据。
- 阻塞本切片的人工决策均为 `decided`。
- Harness 基线通过。

### verification

行为已实现后才进入。此阶段补规则测试、页面状态、人工黄金旅程、干净重启和证据，不允许通过降低验收标准来完成计划。

## 每份计划的最小结构

```markdown
# 计划名称

- 类型：business-feature
- 功能：CUS-001
- 当前阶段：specification
- 状态：active
- 最近更新：YYYY-MM-DD

## 目标
## 范围与非目标
## 事实来源
## 前置门禁
## 验证路径
## 风险与阻塞
## 进度日志
- [ ] 当前步骤：一条可直接执行的动作
## 开放决策
## 中断恢复点
```

## 事实来源写法

必须列出可直接打开的路径和精确章节，并说明用途，例如：

```markdown
- `docs/product-specs/customers.md`：当前业务规则与验收。
- `docs/references/requirements/06-客户模块.md §2.1、§2.4～§2.6`：字段、操作与原始业务描述。
- `docs/references/requirements/01-整体架构与首页.md §4～§5`：全局页面规则和角色权限资料。
```

截图、竞品、行业惯例只能标为 `reference-only`，不能作为业务规则来源。若使用工程推导，必须标为 `engineering-constraint` 并说明它不会改变业务含义。

## 开放决策与人工协助

AI 可以自行决定：符合现有架构的代码拆分、组件复用、测试组织、明显虚构的 Mock 内容和不改变业务语义的视觉细节。

以下必须由人决定：需求冲突、业务字段或枚举、默认值、金额/库存公式、状态转换、角色和数据范围、删除/作废副作用、跨模块形成时点、真实外部动作及范围优先级。

开放决策必须使用表格：

| 决策 ID | 缺失事实与证据 | 可选方案及影响 | 阻塞范围 | 可安全继续 | 决定人 | 状态 | 结论与写回位置 |
|---|---|---|---|---|---|---|---|

状态只允许 `open`、`decided`、`not-applicable`。`decided` 必须记录用户确认的明确结论、日期以及已写回的产品规格位置；仅在聊天中得到答案、只改状态或写“已确认”都不算完成。AI 应先完成不受影响的规格或技术工作，再一次性向用户提出少量、具体、带推荐和影响的问题；不得用模糊问题把整个任务推回用户。

## 验证证据

验证路径必须同时包含：

- 精确自动命令、测试名称和实际结果。
- 正常、边界、失败、慢响应、空数据和无权限场景。
- 业务黄金旅程的起点、操作、预期数据变化和最终可见结果。
- 规则 ID、字段契约条目和测试之间的追踪关系。
- 1280px 页面检查、键盘与错误恢复；重要页面需保留截图路径。
- 重置 Mock 后重跑，以及干净停止/启动后的结果。

“已测试”“看起来正常”“构建通过”不能单独作为业务完成证据。

## 动态维护与恢复

- 开工时写清目标、非目标、事实来源、前置门禁和可验证完成条件。
- 实施中记录实际决策、已运行验证、发现的风险和下一步；计划不是一次性说明。
- 中断前更新“中断恢复点”：最后完成事项、当前阶段、代码和数据现场、下一条动作、已修改文件、最近验证及未决问题。
- 恢复时先核对产品目录、质量状态和 Git 现场是否与计划一致；冲突时先修复事实记录。
- 规格提取发现目录未登记的多义、冲突或缺失事实时，先在产品规格索引新增 `DEC-*`，再在计划中引用；“目录未列出”不等于可以自行决定。
- 完成时确认行为、验证、文档、质量证据和干净重启均完成，再移入 `completed/`。
- 真实但延期的工程问题进入技术债；未确认业务问题留在产品规格的人工决策门，不伪装成技术债。
