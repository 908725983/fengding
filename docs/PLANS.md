# 执行计划

执行计划保存跨会话工作现场，使下一位 AI 只依赖仓库就能继续，不依赖聊天记录，也不能借“先做再说”绕过产品规格。计划以可交付批次为单位，不再要求每个小页面重复建立一套相同现场。

## 何时必须建立计划

- 一个独立高风险业务切片，或一组来源、领域和数据模型高度相关的业务切片。
- 工作会跨会话、影响多个步骤、状态流转、数据契约或架构边界。
- 验证、迁移、外部能力或回退风险较高。
- 存在尚未决定、会改变用户行为或数据结果的问题。

纯文字修正、不改变行为的局部样式修复，以及可在一个会话内完成并由现有专项测试覆盖的低风险维护可以不建计划，但仍需运行相关验证并同步事实文档。

## 位置与唯一现场

- 进行中：`docs/exec-plans/active/YYYY-MM-DD-short-topic.md`
- 已完成：`docs/exec-plans/completed/YYYY-MM-DD-short-topic.md`
- 已确认但有意延期的工程问题：`docs/exec-plans/tech-debt-tracker.md`

同一时间最多一个业务 active plan；它可以是单切片 `business-feature`，也可以是批次 `business-batch`。产品规格索引记录“有什么、能否提取规格、是否达到编码门”，总体顺序记录“先后关系”，active plan 只记录“当前怎么做和做到哪里”，质量评分只记录当前等级与证据入口，不手工复制全部历史进度。

## 计划头信息

每份计划必须包含：

```markdown
- 类型：business-feature | business-batch | integration | harness | architecture | maintenance
- 功能：CUS-001                 # 批次可写 CUS-002,CUS-004,CUS-005；非业务计划写“不适用”
- 风险等级：L1                 # 业务计划必填：L1 | L2 | L3
- 当前阶段：specification       # specification | implementation | verification | audit
- 状态：active
- 最近更新：YYYY-MM-DD
```

业务计划中的每个功能 ID 都必须存在于 `product-specs/index.md`：

- `business-feature`：一个独立切片，适用于金额、库存、复杂状态机等不应与其他实现混杂的工作。
- `business-batch`：两个或多个同领域或天然依赖的切片，共用事实模型、组件或验收旅程；每个 ID 仍独立满足来源、准备度、依赖、决策和完成证据，计划内必须为每个 ID 保留可恢复检查点。
- 批次不得把无依赖关系的高风险状态机强行捆绑，也不得借合并计划绕过任一切片的字段契约。
- 真正不可拆分的跨域事务先在设计文档说明；多个依赖切片完成后的端到端验证使用 `integration` 计划，功能写“不适用”，引用一个或多个 `FLOW-*`，只验证既有契约的组合结果，不新增业务规则。由同一共享 Runtime 整改触发的多条流程可以在一个 integration 计划中验收，但每条流程分别给出结论。

## 风险等级

| 等级 | 适用范围 | 必须保留的验证 |
|---|---|---|
| `L1` | 只读页面、报表、标准主数据 CRUD、无跨域副作用 | 原文字段/操作、normal、empty、表单校验、适用权限、专项测试 |
| `L2` | 单领域状态流转、导入导出、可恢复编辑或删除 | L1 + error/retry、合法/非法状态、关键边界、失败后现场不变 |
| `L3` | 金额、库存、结转、跨领域写入和不可逆副作用 | L2 + 幂等、并发冲突、原子回滚、守恒、从零黄金旅程 |

`slow` 由共享异步基础设施统一验证；`partial-failure` 只用于多个独立 provider 的聚合页面；`unavailable` 只用于真实外部能力或明确延期的依赖。不能为了凑场景数给每个页面制造九类状态。

## 业务阶段门禁

### specification

允许阅读原始资料、建立字段与交互契约、记录人工决策、准备验收和 Mock 契约；不得开始业务实现。计划必须引用精确产品规格、原始文件和章节，不能只写“相关需求”。

### implementation

业务计划中的每个功能只有在以下条件全部满足后才能进入；`business-batch` 在 specification 阶段可以依次提取各功能，但只有批次内全部功能 ready 后，计划整体才进入 implementation：

- 产品规格索引中的字段准备度为 `ready`。
- 对应领域规格存在完整的“`<功能ID> 字段与交互契约`”。
- 依赖切片均有 passing 证据。
- 阻塞本切片的人工决策均为 `decided`。
- Harness 基线通过。

### verification

计划范围内的行为已实现后才进入。此阶段按风险等级补规则测试和黄金旅程；同一批次只在收尾运行一次全量验证、Mock reset 与干净重启，不允许通过降低业务验收标准来完成计划。

### integration

关联切片各自完成不等于业务闭环完成。长期顺序中的阶段出口必须另建 `integration` 计划，并同时满足：

- 在同一个应用级共享 Mock Runtime 中执行，跨路由后仍读取同一份业务事实。
- 从 Mock reset 后本次新建的源头业务单据开始，不使用预置订单、出入库、应收应付、收付款、核销或退单证明主链路。
- fixture 可以提供客户、商品、价格、授权、仓库、库存批次和资金账户等主数据；计划必须明确哪些是主数据、哪些是本次创建的业务单据。
- 记录贯穿全链路的业务关联标识，例如订单号、出库单号、应收单号、收款单号和核销单号，并证明它们属于同一条旅程。
- 同时核对 UI 可见结果、各 Repository 的数量/金额守恒、权限和失败回滚；仅拼接多个模块各自的预置演示不算集成证据。

集成计划完成后才能把 `implementation-sequence.md` 对应 `FLOW-*` 标为 `passing`。一个计划可以覆盖多条共用整改的流程，但每个 `FLOW-*` 必须有独立的旅程、关联编号、守恒结果和通过/阻塞结论。模块可以保持自己的完成记录，但质量评分必须把“模块通过”和“阶段闭环”分开。

## 每份计划的最小结构

```markdown
# 计划名称

- 类型：business-feature
- 功能：CUS-001
- 风险等级：L2
- 当前阶段：specification
- 状态：active
- 最近更新：YYYY-MM-DD

## 目标
## 范围与非目标
## 事实来源
## 前置门禁
## 验证路径
## 风险与阻塞
## 进度日志
- [ ] 当前步骤：一条可直接执行的动作
## 开放决策
## 中断恢复点
```

`business-batch` 额外包含 `## 批次切片状态`，逐行记录功能 ID、当前阶段、最后检查点、下一动作和结果。计划仍只有一个“当前步骤”，按依赖顺序推进；中断后从该表和恢复点继续，不重做已完成切片。

## 事实来源写法

必须列出可直接打开的路径和精确章节，并说明用途，例如：

```markdown
- `docs/product-specs/customers.md`：当前业务规则与验收。
- `docs/references/requirements/06-客户模块.md §2.1、§2.4～§2.6`：字段、操作与原始业务描述。
- `docs/references/requirements/01-整体架构与首页.md §4～§5`：全局页面规则和角色权限资料。
```

截图、竞品、行业惯例只能标为 `reference-only`，不能作为业务规则来源。若使用工程推导，必须标为 `engineering-constraint` 并说明它不会改变业务含义。批次计划必须分别列出各功能的领域规格与原文章节，不能用一个宽泛章节代替全部来源。

## 开放决策与人工协助

AI 可以自行决定：符合现有架构的代码拆分、路由命名、URL 是否保存纯展示筛选、组件复用、测试组织、Mock 场景名称、fake adapter 技术格式、明显虚构的 Mock 内容和不改变业务语义的视觉细节。这些选择写作 `engineering-constraint` 或沿用全局规范，不建立产品人工决策。

以下必须由人决定：需求冲突、会改变结果的业务字段或枚举、业务默认值、金额/库存公式、状态转换、角色和数据范围、删除/作废副作用、跨模块形成时点、真实外部动作及范围优先级。分页默认值已有全局原文时直接复用，不重复提问；纯路由、query、截图、测试场景和实现层版本号不属于产品决策。

开放决策必须使用表格：

| 决策 ID | 缺失事实与证据 | 可选方案及影响 | 阻塞范围 | 可安全继续 | 决定人 | 状态 | 结论与写回位置 |
|---|---|---|---|---|---|---|---|

状态只允许 `open`、`decided`、`not-applicable`。`decided` 必须记录用户确认的明确结论、日期以及已写回的产品规格位置；仅在聊天中得到答案、只改状态或写“已确认”都不算完成。AI 应先完成不受影响的规格或技术工作，再按一个业务批次一次性提出少量、具体、带推荐和影响的问题；不得按页面拆成多轮重复确认，也不得用模糊问题把整个任务推回用户。

## 验证证据

验证路径必须包含：

- 精确自动命令、测试名称和实际结果；开发过程中优先运行专项测试，批次收尾才运行一次 `npm run verify`。
- 对应风险等级要求的场景，不重复验证不适用状态；选择或排除 `slow`、`partial-failure`、`concurrent`、`unavailable` 时写明适用理由即可。
- 业务黄金旅程的起点、操作、预期数据变化和最终可见结果；L1 可以使用一个代表性 CRUD/报表旅程，L3 必须覆盖完整高风险任务。
- 规则 ID、字段契约条目和测试之间的追踪关系。
- PC 管理后台在一个代表性 1280px 页面检查关键布局、键盘与错误恢复；只有布局机制不同的页面追加检查。390px 仅用于公开分享页、商城/小程序预览或需求明确的移动页面。
- 同一业务批次收尾执行一次 Mock reset 与干净停止/启动；已有共享脚本单测覆盖的哈希一致性不在每个切片手工重复记录。
- 截图只保留关键黄金旅程、视觉回归或难以由自动断言表达的证据，不把逐页截图作为完成门禁。
- 若涉及跨模块，明确共享 Runtime 标识、源头新建单据、全链路业务编号、各阶段前后值和最终守恒表；预置业务单据只能用于列表、边界和失败场景，不能替代黄金主路径。

“已测试”“看起来正常”“构建通过”不能单独作为业务完成证据。

## 动态维护与恢复

- 开工时写清目标、非目标、事实来源、前置门禁和可验证完成条件。
- 实施中记录实际决策、已运行验证、发现的风险和下一步；计划不是一次性说明。
- 中断前更新“中断恢复点”：最后完成事项、当前阶段、代码和数据现场、下一条动作、已修改文件、最近验证及未决问题。
- 恢复时先核对产品目录、质量状态和 Git 现场是否与计划一致；冲突时先修复事实记录。
- 规格提取发现目录未登记的多义、冲突或缺失事实时，先在产品规格索引新增 `DEC-*`，再在计划中引用；“目录未列出”不等于可以自行决定。
- 完成时确认行为、风险分级验证、文档和质量证据均完成；批次收尾验证与需要的干净重启完成后再移入 `completed/`。
- `business-feature` completed 只证明对应切片；`business-batch` completed 必须逐个列出各功能 ID 的结果和回退检查点。阶段出口只有在相应 `integration` completed 且 `FLOW-*` 为 `passing` 后才能宣称闭环。
- 真实但延期的工程问题进入技术债；未确认业务问题留在产品规格的人工决策门，不伪装成技术债。
