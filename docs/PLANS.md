# 执行计划规则

## 什么时候必须建计划

跨两个以上领域、改变状态流转/架构边界、预计超过半天或存在未决业务问题时，先在 `docs/exec-plans/active/` 建计划。小型样式修复可直接做，但仍需更新功能状态和验证证据。

## 计划结构

每份 active plan 使用 `docs/exec-plans/TEMPLATE.md`，至少包含：目标、非目标、事实来源、依赖、影响范围、里程碑、验收命令、人工黄金旅程、决策记录、风险与回退，以及可直接恢复的中断检查点。

## 生命周期

1. 在 `feature_list.json` 选择一个功能设为 `in_progress`。
2. 创建或更新 active plan，先写可验证的完成条件。
3. 实现期间持续记录决策和实际验证，不把计划当作开工前的一次性文档。
4. 全部条件满足后把功能改为 `passing`，将计划移至 `completed/`。
5. 遇到需求缺口设为 `blocked`，写明需要谁决定什么；不要自行补齐。

同一时间最多一个功能为 `in_progress`。`not_started` 不代表不存在需求，`blocked` 不代表失败。

## 状态字典

- `not_started`：已有规格，尚未实现。
- `in_progress`：当前唯一正在实施的功能。
- `passing`：实现和验收证据均已完成。
- `blocked`：缺少必要事实或外部前提，当前不得实施。

## 证据要求

证据必须能被下一位开发者复核：命令与结果、测试名、人工步骤、截图路径或明确的评审记录。仅写“已测试”“看起来正常”不算证据。

## 中断与恢复

任务即使没有完成，也不能只把进度留在聊天里。中断前必须在 active plan 的“中断恢复点”记录：最后完成事项、当前代码状态、下一条具体动作、已修改文件、最近验证结果和未决问题，并在 `progress.md` 增加会话记录。

恢复时先按 `AGENTS.md` 的开工顺序读取仓库状态。如果 active plan 与 `feature_list.json` 冲突，停止开发并先修复状态；不得凭聊天记忆选择继续位置。
