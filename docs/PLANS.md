# 执行计划

执行计划保存跨会话的工作现场，使下一位开发者只依赖仓库就能继续，不依赖聊天记录。

## 何时必须建立计划

- 工作会跨会话或预计需要多个明确步骤。
- 同时影响多个子系统、架构边界、状态流转或数据契约。
- 验证、迁移、发布或回退风险较高。
- 存在尚未决定、会显著改变实现结果的问题。

很小且可一次完成的局部修复可以不建计划，但仍要运行验证并同步相关事实文档。

## 位置与命名

- 进行中：`docs/exec-plans/active/YYYY-MM-DD-short-topic.md`
- 已完成：`docs/exec-plans/completed/YYYY-MM-DD-short-topic.md`
- 已确认但有意延期的工程问题：`docs/exec-plans/tech-debt-tracker.md`

active 目录只保留真正进行中的计划。同一时间只设置一个清晰的“当前步骤”；完成后移动整个计划，保留历史证据。

## 每份计划的最小结构

```markdown
# 计划名称

- 状态：active
- 最近更新：YYYY-MM-DD

## 目标
## 范围与非目标
## 事实来源
## 验证路径
## 风险与阻塞
## 进度日志
- [ ] 当前步骤：一条可直接执行的动作
## 开放决策
## 中断恢复点
```

验证路径必须写明自动命令和人工黄金旅程；“已测试”不是证据。开放决策要描述缺失事实、影响范围和需要谁决定，不自行补造答案。

## 动态维护

- 开工时写目标、非目标、事实来源和可验证完成条件。
- 实施中记录实际决策、已运行验证、发现的风险与下一步；计划不是一次性开工说明。
- 中断前更新“中断恢复点”：最后完成事项、当前代码状态、下一条动作、最近验证、未决问题。
- 完成时确认行为、验证、文档和干净重启均有证据，再把状态改为 completed 并移动到 `completed/`。
- 真实问题若决定延期，转入技术债台账；模糊愿望和未确认猜测不登记为技术债。
