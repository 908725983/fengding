# AI 工程护栏

## 目的

本文件规定实际开发中最容易被 AI 猜测、简化或误判的事项。任何实现与本文件冲突时，以本文件为准；无法满足时停止相关功能并记录问题，不能用“先做出来再说”绕过。

## 事实优先级

发生冲突时按以下顺序判断：

1. 用户最新明确确认、且已写入 `docs/DECISIONS.md` 的决定。
2. `docs/product-specs/` 中的业务规则和验收标准。
3. `docs/ui-specs/` 中从原需求提取的页面字段契约。
4. `docs/references/source-requirements.md` 登记的原始需求文档。
5. `ARCHITECTURE.md`、`FRONTEND.md`、`MOCK.md` 的工程约束。
6. 现有代码只能说明当前实现，不能覆盖业务规格。

参考产品、行业惯例、AI 记忆和“通常系统都这样做”均不是业务事实来源。

## 不确定事项分级

| 等级 | 典型问题 | 处理方式 |
|---|---|---|
| A：必须阻塞 | 金额、库存、状态流转、权限、删除/作废、单据关系、真实外部副作用 | 在 `OPEN_QUESTIONS.md` 登记；相关最小功能标记 blocked，等待确认 |
| B：可局部延期 | 某个标签含义、非主路径统计口径、外部模拟细节 | 不实现该局部能力，页面明确“待确认”；不阻塞无关主路径 |
| C：可逆设计选择 | 间距、非业务文案、普通占位图、低风险交互细节 | 使用 `FRONTEND.md` 默认值，必要时记录 decision，不询问业务规则 |

AI 不得把 A 类问题降级为 C 类，也不得因为一个 B 类问题阻塞整个模块。

## 开发前门禁

业务功能进入 `in_progress` 前必须同时完成：

1. 找到对应 product spec 和规则 ID。
2. 从原始需求提取本功能页面字段到 `docs/ui-specs/`。
3. 在 `feature_list.json` 填写 `ui_spec` 和 active plan。
4. 对照 `OPEN_QUESTIONS.md`，确认没有未处理的 A 类问题。
5. 写出正常路径、失败路径、权限路径和 Mock 重置后的验收步骤。

缺少任一项时不得开始堆页面。

## 常见风险与强制处理

| 开发场景 | AI 容易犯的错误 | 必须做法 |
|---|---|---|
| 页面字段 | 根据截图补列、改字段名、猜默认值 | 逐字段写入 `ui_spec`；需求没写则标记未定义，不设为必填 |
| 筛选和分页 | 只在前端数组过滤，分页总数不一致 | 定义查询契约；筛选、排序、分页由 repository 返回同一结果集 |
| 表单 | 只做“看起来能填”，遗漏联动和只读来源 | 记录控件、必填、默认、来源、校验、权限、联动和错误位置 |
| 状态流转 | 按钮直接改字符串，允许跳级或回退 | 使用领域 command/状态机；服务端边界再次校验允许动作 |
| 权限 | 只隐藏按钮，直接调用仍能成功 | 路由、可见性和 service command 三层一致；拒绝时返回明确原因 |
| 金额 | 使用浮点数、前端各自算总额 | 内部统一整数分；计算集中在 service，保留明细和舍入依据 |
| 数量和单位 | 把箱、件、公斤当成同一数字 | 数量必须带单位；换算通过商品单位规则，未知换算不得默认 1:1 |
| 库存 | 页面顺序执行扣库和建单，失败后留半状态 | 跨领域协调服务返回单一结果；支持幂等 request ID 和失败回滚 |
| 删除/作废 | 物理删除有关联单据的数据，或混淆删除与作废 | 查规格中的生命周期；有关联记录时使用下架/作废并保留审计 |
| 编号 | 用随机数、硬编码前缀或允许修改 | 通过编号服务生成；前缀/序号规则未确认时登记问题 |
| 日期与定时 | 使用机器本地时间导致测试漂移 | ISO 8601 + Asia/Shanghai；定时规则使用可控模拟时钟 |
| 自动任务 | 刷新页面时偷偷触发“定时生效” | 由明确 scheduler/fake clock 触发并留下执行记录，测试边界时刻 |
| Mock | 页面自带数组、随机数据、测试互相污染 | 统一 repository；固定 ID；场景覆盖；每项测试独立重置 baseline |
| 跨模块数据 | 客户、仓库、商品在多个模块各存一份 | 确定唯一领域所有者，其他模块只用公开 provider/repository |
| 错误处理 | 所有失败都提示“操作失败” | 使用结构化错误码；区分校验、冲突、权限、网络和系统错误 |
| 加载与提交 | 慢请求期间可重复点击造成重复单据 | 明确 loading；写操作防重复；服务仍需幂等，不能只禁按钮 |
| 空状态 | 把无数据、无结果、无权限、加载失败混为一谈 | 四种状态分别呈现并给出不同下一步 |
| 外部能力 | 调真实支付/地图/企微，或假装模拟结果是真实回执 | 只能 fake adapter，界面标记“原型模拟”，不使用真实凭据/数据 |
| 导入导出/打印 | 只放无响应按钮就标记完成 | 未实现标记“规划中”；模拟时展示校验结果或预览，不声称真实文件完整 |
| UI 风格 | 临时写颜色和尺寸、照抄参考产品 | 使用 token 和共享组件；参考产品只提供风格线索 |
| 响应式 | 只在开发者屏幕验证 | 至少检查 1280px 与 720px；表格可局部滚动，页面主体不能意外溢出 |
| 依赖升级 | 为一个小功能升级框架或引入大组件库 | 先写 active plan 的理由、替代方案、包体和兼容影响，再修改依赖 |
| 重构 | 顺手修改无关领域，扩大变更范围 | 只改当前功能必要边界；额外债务进入计划，不夹带大范围重构 |
| 测试 | 只测成功路径，或修改断言适应错误实现 | 规则 ID 对应测试；至少覆盖边界/拒绝路径；不弱化验证制造 passing |
| 占位功能 | 有菜单和页面就标记完成 | 占位页保持 `not_started`；只有行为、测试和证据齐全才 passing |

## 字段决策规则

- 原需求明确字段：保持业务名称、类型、必填性和只读性，不擅自改语义。
- 原需求只给名称未给控件：选择最小可逆控件，并在 `ui_spec` 标注“设计补充”，不能伪装成业务规则。
- 原需求未给默认值：默认空；不得为了演示方便自动填真实含义值。
- 原需求字段矛盾：登记问题；高风险字段阻塞相关提交，低风险字段可隐藏或只读延期。
- 计算字段：必须写公式、输入、精度、刷新时点和为空行为。
- 枚举字段：必须列出值、显示文案、颜色语义、允许动作和未知值回退。
- 敏感字段：先按最小可见原则处理；完整显示规则未定义时不能默认所有角色可见。

## 变更规则

- 用户改变需求时先更新 decision、product spec、ui spec 和验收，再改代码。
- 删除需求也要保留决策记录，避免后续 AI 从旧截图或旧代码恢复。
- 发现代码和规格不一致时，不默认代码正确；先判断是实现缺陷还是未回写的需求决定。
- 新增业务规则必须获得可追踪 ID；相关 service 和测试引用该 ID。

## 必须停止并记录的情况

- 两份有效规格给出相反业务行为。
- 不清楚某动作是否改变钱、库存、权限或不可恢复状态。
- 需要真实凭据、生产数据或外部账号才能继续。
- 需要绕过验证、删除证据或弱化规则才能通过。
- 当前功能依赖的上游功能没有实现且不能用公开稳定契约隔离。

停止只影响最小相关功能；仍可继续不依赖该问题的安全工作。

## 完成前反向检查

提交 `passing` 前逐项回答：是否实现了规格而非截图；是否有直接读 fixture；是否存在浮点金额；是否只隐藏权限按钮；是否覆盖重复提交；是否能重置复现；是否把占位动作当成完成；是否留下恢复点和可复核证据。任何一项答案不确定都不能 passing。
