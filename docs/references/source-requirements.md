# 需求来源

## 仓库内快照

八份原始需求已逐字复制到 `docs/references/requirements/`，并由 `requirements-manifest.json` 记录文件名、SHA-256、字节数和行数。快照用于可移植阅读与变更检测，不直接在其中编辑。

业务实现时先阅读相关快照，再把已确认的页面行为、字段、业务规则和验收写入 `docs/product-specs/`。产品规格是当前实现入口，快照是上游材料；二者冲突时停止受影响实现并在 active plan 记录具体差异。

快照内容详细不等于全部可直接编码：原文中明确写“待确认”“建议”、只有状态名称但没有转换、或跨文件形成时点不完整的内容仍是规格缺口。功能、原文章节、依赖、字段准备度和已知人工决策统一登记在 `../product-specs/index.md`，AI 不得只读一个段落就补全周边规则。

## 从原文到代码的唯一流程

```text
原始需求快照
  -> 产品规格中的功能字段与交互契约
  -> active plan 的范围、门禁和验证
  -> Types/Schema/Service/UI
  -> 测试与 QUALITY_SCORE 证据
```

- 原始快照只读；不要为了让实现合理而修改原文。
- 产品规格必须写精确文件和章节，区分原文事实、人工决定与工程约束。
- 原文未定义的字段和行为写“未定义”，进入人工决策门；不能把 Mock 示例值当成默认业务值。
- 上游发生变化时先对比差异、评审影响，再更新快照、manifest、产品规格、计划和测试；不得自动覆盖已实现契约。
